# 开发与 GitHub 发布规范

本规范适用于 WhaleLife 主干和独立插件仓库。由专门的发布会话统一管理远端提交，开发会话负责实现、验证和本地提交。用户明确指定的发布范围优先于本文默认流程。

**先遵守[不许越权开发](PLUGINS.md#不许越权开发)。** 本文的“完成”“验证”“提交”“交接”均指用户已授权的范围，不授权补改其他仓库。发现跨项目缺口先说明，不因发布受阻自行修复。开发授权不自动包含安装、真实测试、外发或发布；已有明确授权不重复确认。

## 1. 职责与交接

- 开发会话：只改负责的项目，完成必要测试和文档，按明确文件列表做本地提交；不再自行 push、创建远端标签或 GitHub Release。一个阶段完成后交接一次，不为每个小修改反复交接。
- 发布会话：核对来源、提交内容、测试证据、隐私和许可证，整理可发布提交，推送并回读确认。只处理用户授权的项目和明确交付的版本。
- 业务问题退回原开发会话，发布会话不顺手修改业务代码、跨项目补功能或部署运行中的机器人。明确授权的发布说明、版本和打包元数据可由发布会话维护；影响构建产物时补对应检查。
- 本地 commit、GitHub push、Release 和本机部署分别记录。更新源码不自动代表需要打标签、发安装包或重启服务。
- 只有用户授权的协作才联系其他会话；不得替用户给开发会话追加任务。发现问题先给出具体文件、版本、影响和待解决事项。

开发交接使用以下简表，不附私人配置或完整日志：

```text
项目及目标仓库：
来源工作区：
基线提交 → 待发布提交（或明确文件白名单及补丁）：
改动和用户可见效果：
测试命令、结果、对应提交；未验证内容：
兼容性、迁移、配置和许可证影响：
原地升级验收（有上一正式版的官方商店插件）：宿主版本/提交、旧版 → 候选版、商店确认应用的结果、升级前后启停状态、配置与样例数据、失败及复验记录
允许的动作：本地提交 / 推送分支 / 指定标签或 Release
排除内容和已知风险：
```

### 本体发行包

主干 `package.json` 的 `version` 是 WhaleLife 本体版本。日常提交可以共用当前开发版本。每次正式发版都要升版本，并同步 `package-lock.json` 的顶层和根包版本。例如，当前用户已在运行 `v0.1.0`，下一次修复发布可用 `v0.1.1`。控制台从 `iinukami/whalelife` 的正式 GitHub Release 查找更高版本。

1. 将升版与这次交付内容一起纳入待发布提交。在新宿主上复验官方及社区商店的旧发行包，包括子插件沿用已安装父插件的路径。保留旧包的最低实测宿主 `hostRange`，按各包声明的上界、平台、架构与插件依赖验收。新增宿主能力成为必需条件时，再为依赖该能力的新包提高最低版本。验收时可用 `node tools/build-host-release.mjs <输出目录>` 从 Git 索引预打包，在隔离实例验证从旧版本确认升级、重启和失败回滚。升级成功后，在已切到候选包的控制台打开插件商店，用已安装的旧插件手动检查更新，核对列表和详情里的目标版本，并实际确认一次更新，验证原配置和样例数据。记录本体包摘要与插件升级前后的版本。
2. 待提交进入公开 `main` 后，检出该提交，运行 `node tools/build-host-release.mjs --release <输出目录>`。正式打包会读取公开主干及其版本标签，确认该提交已合入，并要求版本高于已部署基线及主仓使用过的所有正式版本号。输出包含提交 SHA、标签、包路径、字节数与 SHA-256。核对正式包与已验收的包摘要一致。
3. 按授权在输出的提交上创建对应的新标签 `vX.Y.Z`，上传 `whalelife-vX.Y.Z.wlhost.gz` 并核对 GitHub 返回的大小和 SHA-256，再公开正式 Release。若标签已被另一笔发布占用，保留原标签和附件，重新确定版本。恢复同一次中断的草稿发布时，先核对原标签提交与已验收附件的摘要。

涉及启动器迁移时，另用上一正式版的原装安装目录，从概览连续确认两次本体更新。验证第二次更新确实完成、手动停止和冷启动走原入口、插件状态和资料保留，并覆盖迁移中断和预检回滚。如果调整了要持久化的启动器文件，审核对应差异，核对并更新 `core/host-launcher-migration.ts` 中的组合摘要，运行 `tests/host-launcher-migration.test.ts`。

安装根目录及原始启动入口须保留。活动程序在 `.whalelife-updates/releases/` 中，程序版本通过状态文件选择。正式发布的程序必须兼容现有启动协议和资料快照范围。该版本包适用于使用纯 JavaScript 运行依赖的主干。

## 2. 发布流程

1. 核对工作目录、remote、分支、HEAD、暂存区和未提交改动，fetch 目标远端。只处理交接给出的提交或文件；混有其他会话改动时保留，不能用 `git add .`、reset 或 clean 清场。
2. 审查目标远端基线之后的全部拟发布提交及最终差异，检查文件范围、作者身份、依赖和产物。不能只检查最后一个提交，也不能把运行目录整体复制为源码。来自私人或已清理旧历史的工作区只转移审查过的文件补丁，不能 merge/push 其历史。
3. 核验隐私、分仓、许可和必要测试。已有测试证据对应相同代码和依赖时可以复用；合并、冲突解决、依赖变化或产物变化后补跑受影响检查。纯文档变更不重复运行全部业务测试。
4. 明确 stage 本次文件；提交前再次审查 staged diff。本地提交已经完整时直接审核，不为制造“发布提交”重写历史。记录实际待推送 SHA；如果共享目录被继续修改，重新核对范围，不顺手包含后来改动。
5. 常规采用正常快进推送。远端前进先核对新增内容，禁止强推覆盖。删除远端分支/标签、改变仓库可见性、重写已公开历史等操作必须有用户针对该操作的明确授权。
6. 推送后核对远端 SHA、仓库和分支，检查工作区仍保留他人改动。交付时给出提交链接、内容、验证和未发布项。多仓库分别报告成功或失败，不把部分成功说成全部完成；不为回滚一仓而擅自改动其他仓。
7. 每次从独立副本更新公开 `main` 或发布正式版本，发布会话都要回到该项目日常开发使用的源码仓库，重新 `git fetch origin main`。核对仓库地址、当前分支和未提交改动后，在干净的本地 `main` 上执行 `git merge --ff-only origin/main`。用 `git rev-list --left-right --count main...origin/main` 核对：两端一致为 `0 0`；本地已有后续提交时，可以保留本地领先，右侧必须为零。若两边都有独有提交，保留双边历史，在独立副本合并并测试，再按发布授权同步两端。交付时记录公开与本地提交和仍待推送的改动。运行实例目录不参与源码同步。

用户已明确授权某次发布且上述检查通过时，继续完成，不重复索要相同确认。没有明确范围的脏工作区不是待发布清单。

## 3. 隐私与分仓

禁止发布真实 API Key、密码、Cookies、令牌、登录态、账号连接配置、聊天记录、机器人记忆、共享/独立事实、私人个性化人格、日志和备份。检查范围包括本次引入的 Git 历史、源码、测试夹具、文档、截图及拟上传的安装包；`.gitignore` 不能代替审查已跟踪文件。

纯示例配置、空白目录结构、公开默认人格、虚构测试材料可以保留。检查时只报告文件位置、类别和是否命中，不把秘密原值打印进工具输出、聊天、提交说明或工单。发现真实泄漏立即停止相关发布并报告，不自行把私人原文发给第三方。

每个插件独立仓库，只携带自己的源码、文档和必要测试。允许依照公开契约依赖其他插件，不复制其他插件源码或实际 data 目录。主干不包含已安装插件的实现和私有数据。打包前核对实际文件清单，不上传开发目录压缩包。

## 4. 验证与兼容

- 主干核心契约/生命周期变更：`npm run check`、`npm run test:compat` 和受影响专项；其他变更按实际影响验证。
- 插件：按本仓库命令运行类型检查、专项/业务测试和受影响构建；涉及宿主契约时验证声明支持的最低宿主和当前宿主。
- 不修改冻结的旧插件样本、基线或断言来让不兼容改动通过。保留主干兼容标签 `213b52b`；它是旧插件验证入口，不是可随意移动的“最新版本”。
- 不以一个项目升级为理由要求其他合规项目配套修改。失败应由违反契约的一方修复。测试、真实平台运行和部署验证分别说明。
- 常规发布不调用付费模型、不操作正式账号或用户记忆，不运行 `tests/acceptance.ts`。测试使用本仓库提供的临时目录清理机制。
- 未实际运行的 CI 不能声称通过；本地验证证据需记录对应代码版本。

## 5. 许可与产物

维护现有 `LICENSE`、`LICENSE-ADDITIONAL`、`NOTICE.md`、`THIRD_PARTY_NOTICES.md` 以及代码版权/SPDX 声明。原创代码采用 AGPL-3.0-only 和仓库现有附加条款；不能替第三方重新授权。重新分发第三方材料时依据其实际许可证检查，不凭仓库拆分或进程隔离判断许可豁免。

插件构建必须保留法律文件和现有清单/哈希校验。QQ 相关第三方运行组件单独遵守其许可，不能将包含 NapCat/QQ 等外部组件的整个发行物标成统一 AGPL 或笼统承诺可商用。源码推送不自动授权上传这些第三方二进制文件。

### 官方插件何时打包

每次用户要求检查或发布更新时，按插件比较本次拟发布的源码与商店当前版本对应的源码、文件清单。开发会话在交接中注明改动是否影响安装后的行为或随包文件，以及对应的测试。发布会话在用户授权整次更新发布后，负责判断哪些插件需要新包，并完成相应的构建、验包和发布，无需为每个插件或步骤重复确认。检查由用户发起。

发布含用户可见变更的插件时，在同一次发布中准备安装包、推送对应源码、发布插件 Release 并更新商店。源码已先推送时，继续从该提交验包并完成余下步骤。某一步受阻时，交付中写明已完成的步骤、具体原因和当前可安装版本。

- 修复或功能改变了安装后的程序、界面、默认配置、运行依赖、资源或迁移逻辑，或随包说明、许可、构建方式的变化需要交付给用户时，按插件现有版本约定确定新版本。同一批更新可合为一个包。仅修改仓库说明、测试或开发工具且不影响发行文件时，保留现有包和版本。
- 构建前同步插件版本元数据，锁定含这些变更的源码提交、依赖和构建环境。按插件自己的构建入口生成发行目录，检查实际收录文件、许可及第三方组件，排除开发资料和用户数据。核对文件清单、逐文件及整包 SHA-256、字节数，记录版本、源码 SHA 和验包结果。已公开版本的资产保留原样。
- 为商店发布时，先将已验包上传至对应插件仓库的版本 Release，回读下载地址、大小和摘要，再据此更新主仓发行清单和目录。在隔离宿主从空缓存走商店安装，核对依赖、加载结果与实际版本。涉及升级、卸载或数据布局时，用测试配置和样例数据验证相应路径及数据保留。商店清单通过验证后再推送。
- 更新已有正式版的官方插件时，在支持商店原地更新的隔离宿主安装上一正式发行包，准备可辨认的样例数据并设置非默认配置。按用户实际路径检查更新、预览并确认应用，再回读正在运行的版本。记录升级前后父插件与相关子插件的启停状态、预期与实际结果，并核对配置和样例数据。可用 `node tools/trial-official-update.mjs <official-releases.json> <插件 ID> <旧版本> <新版本> [本地发行包…]` 执行商店的更新计划、确认应用及持久文件核对。全新安装、保留数据的卸载重装和原地更新各自记录。仅支持重装的旧宿主可验证其实际路径，原地升级仍需在支持该操作的宿主上验证。
- 带有子插件文件的发行包要分别列明文件归属和各受测宿主上预期启动的插件 ID。在 `bundledPluginIds` 中保留随包组件的归属；只在特定宿主注册的组件同时列入其子集 `conditionalBundledPluginIds`。用各受测宿主原地更新后的实际运行记录核对加载条件。例如，QQ 在支持 `ctx.optional` 的宿主上直接接入独立图库服务，包内 `qq/gallery` 供旧宿主使用。当前宿主应能在没有 `qq/gallery` 运行实例时完成升级。
- 确认应用后若加载失败或触发回滚，在发布记录中写明宿主和插件版本、失败步骤、回滚后的运行版本与启停状态，以及配置和样例数据的核对结果。暂停该版上架，修正后从同一旧发行包重新走完整原地更新流程，保留失败记录并补记复验结果。
- 发布官方父插件新版时，从公开目录列出依赖它的官方和社区子插件。对声明父插件最低兼容版本的发行包，在商店验证三个场景：从空缓存连同父插件一起安装；在旧父版和新父版上分别安装同一份子包；保留已装子插件及其配置，从商店更新父插件并验证子插件的代表性功能。仅在子插件使用了新增的父插件能力时提高最低版本要求。
- 交付时分别说明本地包、GitHub Release 资产和商店收录的实际状态。用户只要求打包时，交付本地已验包、摘要和测试结果；上传资产和商店上架留待相应发布范围。

## 6. 操作边界

不删除或覆盖私人配置、记忆、插件 data、他人未提交改动。不为发布便利关闭机器人或改写运行环境。临时验证文件集中在项目忽略目录并按所属清理；自动审批拒绝时停止该操作、说明具体原因，不换工具绕过。

本规范只规定交付和发布流程；主干能力与问题仍以 [STATUS.md](STATUS.md) 为唯一现状入口，插件契约见 [PLUGINS.md](PLUGINS.md)。
